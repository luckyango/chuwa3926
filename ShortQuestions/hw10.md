# Question 1: Three Pillars of Observability

The three pillars are logs, metrics, and traces.

Logs record specific events, like errors or requests. I usually use them to debug when something goes wrong.
Metrics are numbers over time, like latency or CPU usage. They are more for monitoring and seeing trends.
Traces show how a request flows through different services, which is helpful to understand where time is spent or where something breaks.

# Question 2: Metrics Data Types

There are four common types:

Counter: only increases
Example: total number of requests
Gauge: can go up or down
Example: current memory usage
Histogram: groups values into ranges
Example: request latency distribution
Summary: gives percentile values like p95
Example: tracking p95 response time

# Question 3: Structured Logging

Structured logging means logs are in a consistent format, usually JSON, instead of plain text.

For example:

{ "level": "error", "user_id": 123, "message": "DB timeout" }

It’s better because it’s easier to search and filter, especially in tools like ELK or Datadog. Plain text logs are harder to query and not very scalable.

# Question 4: Distributed Tracing Concepts

A trace represents the full request.
A span is one step in that request (like calling a service or querying a DB).
Context propagation means passing trace info (like trace_id) between services.

So when one service calls another, it sends this context along, and all the spans can be connected into one trace.

# Question 5: Prometheus Pull Model

Prometheus uses a pull model, which means it periodically sends requests to services to get metrics from a /metrics endpoint.

I think the main advantage is that Prometheus controls everything, so it’s easier to manage and works well with dynamic systems like Kubernetes. It also knows when a service is down because it can’t scrape it.

The downside is that services have to expose endpoints, and short-lived jobs might not be captured if they finish too quickly.
