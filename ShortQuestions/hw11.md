# Question 2. Look at the following connection pool code. What will happen when getConnection() is called and the pool is empty but usedConnections.size() == maxPoolSize? Explain the behavior.
```
public Connection getConnection() throws SQLException {
    Connection conn = availableConnections.poll();
    if (conn == null) {
        if (usedConnections.size() < maxPoolSize) {
            conn = createConnection();
        } else {
            conn = availableConnections.poll(maxWaitMs, TimeUnit.MILLISECONDS);
            if (conn == null) {
                throw new SQLException("Timeout waiting for connection");
            }
        }
    }
    usedConnections.add(conn);
    return conn;
}
```
The code will wait for a connection using availableConnections.poll(maxWaitMs, TimeUnit.MILLISECONDS);
If a connection is returned to the pool within maxWaitMs, it will be reused.
Otherwise, it throws SQLException: Timeout waiting for connection
The thread blocks and waits, and may fail with timeout if no connection is released.

# Question 3. The following code attempts to release a Redis distributed lock. What is the problem with this implementation? How would you fix it?
```
public void unlock(String resource, String lockId) {
    try (Jedis jedis = pool.getResource()) {
        String currentValue = jedis.get(resource);
        if (lockId.equals(currentValue)) {
            jedis.del(resource);
        }
    }
}
```
Problem: The implementation is not atomic. A race condition can occur: if the lock expires between the get check and the del command, the code might accidentally delete a new lock held by a different client.

# Question 6. Explain why the following message consumer implementation provides "at-least-once" semantics instead of "exactly-once":
```
@KafkaListener(topics = "orders")
public void consume(Order order) {
    orderService.processOrder(order); // May throw exception
    // Kafka auto-commits offset after this method returns
}
```
This implementation is "at-least-once" because Kafka auto-commits the offset only after the method returns successfully. If orderService.processOrder succeeds but the system crashes before the auto-commit happens, the same message will be redelivered and processed again upon restart

# Question 7. In a connection pool, what is the difference between "test-on-borrow" and "background validation"? Which one has better performance and why?
Difference: "Test-on-borrow" checks the connection synchronously every time it is taken from the pool; "background validation" uses a separate thread to check connections periodically.

Better Performance: Background validation. It removes validation latency from the application's request path, whereas "test-on-borrow" adds an extra round-trip to the database for every single getConnection() call.

# Question 8. Look at the ZooKeeper distributed lock implementation below. Why does it watch the node "before" itself instead of watching all nodes?
```
// Simplified lock acquisition logic
List<String> children = getSortedChildren(); // e.g., [lock-001, lock-002, lock003]
String myNode = "lock-003";
if (myNode.equals(children.get(0))) {
    return true; // Got the lock
}
// Watch the node before me (lock-002), not all nodes
String nodeToWatch = findNodeBefore(myNode);
watchNode(nodeToWatch);
```

It watches only the node immediately before itself to avoid the "Thundering Herd" effect. If every client watched all nodes, a single lock release would trigger a notification to every waiting client simultaneously, causing a massive spike in CPU and network traffic as they all try to grab the lock
